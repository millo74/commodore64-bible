# Article 1 -- Knowledge Belongs to Everyone

The Commodore 64 Bible does not belong to its authors.

It belongs to the knowledge it preserves and to the community that will continue to grow it.

The purpose of this project is to collect, verify, document and share technical knowledge about the Commodore 64 for current and future generations.

---

# Why This Project Exists

The Commodore 64 is one of the most influential computers in history.

It introduced millions of people to programming, digital creativity and computer science.

Many programmers, engineers, musicians and game developers started their journey on this machine.

During its lifetime, an extraordinary amount of technical knowledge was created:

* books;
* magazines;
* technical articles;
* demos;
* commercial games;
* source code;
* programming techniques;
* hardware discoveries.

However, much of this knowledge is scattered across different archives and communities.

The goal of the Commodore 64 Bible is to collect and organize this knowledge into a single, structured and accessible reference.

---

The Commodore 64 Bible aims to become:

# What This Project Is Not

The Commodore 64 Bible is not:

* a piracy archive;
* a collection of undocumented code;
* a simple emulator guide;
* a replacement for original manuals;
* a nostalgic tribute without technical value.

It is a technical and historical research project.

# Fundamental Principles

## 1. Understanding Over Copying

Source code is only valuable when its purpose and design decisions are understood.

Every routine should explain not only what it does, but why it exists.

---

## 2. Accuracy Over Speed

A single verified document is more valuable than many incomplete documents.

Technical information must be checked whenever possible.

---

## 3. Documentation Is Part of the Code

Code without explanation eventually becomes difficult to understand.

Documentation is considered an integral part of every implementation.

---

## 4. Experiments Before Assumptions

Whenever possible, concepts should be demonstrated through practical experiments.

Observe.

Measure.

Verify.

Document.

---

## 5. Historical Respect

The techniques developed by programmers of the 1980s and 1990s represent remarkable engineering achievements.

Their work should be studied and preserved with respect.

---

## 6. Simplicity and Clarity

Optimized assembly code can become difficult to read.

The project values clarity before premature optimization.

Every optimization should have a documented reason.

---

## 7. The Mountain Principle

The Commodore 64 Bible is built around the idea that knowledge is not consumed, but explored.

Learning is not a linear process where information is simply collected and forgotten.

It is a journey.

Every stage represents a step forward.

Every Vista Point represents a moment of reflection.

Every Mountain Hut represents consolidation of acquired knowledge.

Every Summit represents the moment when understanding becomes mastery.

However, reaching a Summit does not mean the journey is complete.

From every peak, new mountains become visible.

Every achievement reveals new questions, deeper concepts and unexplored territories.

The goal of this project is not only to teach the Commodore 64.

The goal is to help people become Commodore 64 programmers.

Knowledge is not a destination.

Knowledge is the trail.

# Scientific Integrity

The Commodore 64 Bible follows a research-oriented approach.

When information is uncertain:

* uncertainty must be clearly stated;
* different theories should be documented;
* assumptions must be identified;
* conclusions should be supported by experiments or historical sources.

---

# Reliability Levels

Documents and discoveries may have one of these reliability levels:

## Verified

Confirmed through testing, documentation or multiple reliable sources.

## Inferred

Derived from technical analysis but not completely confirmed.

## Historical

Based on interviews, magazines, original documentation or personal accounts.

## Experimental

Currently under investigation.

# Programming Philosophy

The project follows these principles:

* meaningful labels are preferred over cryptic names;
* source code should be readable;
* routines should document inputs and outputs;
* registers modified by routines should be specified;
* timing information should be documented when relevant;
* examples should compile correctly.

---

# Assembly Language Standards

The historical reference environment is:

**Turbo Macro Pro compatible syntax**

Modern compatibility targets:

* Kick Assembler;
* other modern 6502/6510 assemblers.

The objective is not only to reproduce old techniques, but to understand them.

---

# International Documentation

English is the canonical language of the project.

Translations may be created by the community.

Every translation must:

* preserve the original structure;
* identify the source document;
* specify the original version;
* keep technical terminology consistent.

All documentation uses UTF-8 encoding.
