# Purpose

The repository is more than a collection of files.

It is the physical representation of the Commodore 64 Bible.

Its structure has been designed to make knowledge easy to discover, maintain and extend over many years.

Every directory exists for a specific reason.

Every document belongs to a well-defined place.

The repository should remain understandable as it grows.

---

# Design Principles

The repository follows a small number of fundamental principles.

* Knowledge before files.
* Simplicity before complexity.
* Consistency before convenience.
* Stable paths over frequent reorganization.
* One logical location for every Knowledge Artifact.

---

# The Two Worlds

The Commodore 64 Bible is organized around two complementary worlds.

## The Laboratory

The Laboratory is the place where ideas are explored.

It contains:

* experiments;
* research;
* reverse engineering;
* prototypes;
* unfinished investigations.

Knowledge inside the Laboratory is considered work in progress.

---

## The Bible

The Bible contains mature knowledge.

Information enters the Bible only after it has been reviewed, verified and documented.

The Bible represents the project's official reference.

---

# Repository Layers

The repository is organized into several logical layers.

## Foundation

Defines the identity of the project.

Examples include:

* README
* Project Philosophy
* Translation Policy
* Repository Architecture
* Knowledge Trail
* Document Classification

---

## Knowledge

Contains all educational material.

Knowledge is organized according to the Knowledge Trail.

Trails contain Stages.

Stages lead to Vista Points, Mountain Huts and Summits.

---

## Research

Contains investigations and technical discoveries.

Research may eventually become part of the official Bible after verification.

---

## Reference

Contains stable technical documentation.

Examples include:

* hardware references;
* memory maps;
* instruction sets;
* timing tables;
* programming interfaces.

---

## Assets

Contains non-document resources.

Examples include:

* source code;
* assembly libraries;
* graphics;
* tools;
* scripts;
* build systems.

---

# Growth Strategy

The repository is expected to grow continuously.

New material should be integrated without changing the existing organization whenever possible.

Backward compatibility of document locations is preferred.

Stable references make long-term maintenance easier.

---

# Naming Philosophy

Names should describe purpose rather than implementation.

Directories and files should remain readable without requiring additional explanation.

Cryptic abbreviations should be avoided unless they are universally recognized.

---

# Documentation First

Documentation is considered part of the implementation.

Whenever new software, research or experiments are added, the corresponding documentation should be added as well.

Knowledge and implementation should evolve together.

---

# Future Evolution

The architecture is intentionally modular.

New Knowledge Artifacts, Trails and research areas may be introduced without redesigning the repository.

The structure is expected to evolve while preserving clarity and consistency.

---

# Final Thought

A repository is not measured by the number of files it contains.

It is measured by how easily knowledge can be found, understood and expanded.

The architecture should serve the knowledge.

Never the opposite.
